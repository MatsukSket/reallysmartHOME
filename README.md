# reallysmartHOME

Локальная демонстрация курсового проекта «Решатель задач интеллектуальной системы „Умный дом“». Браузер обращается к FastAPI. Решатель проверяет команды, шлюз доставляет их симулятору, а карточки получают наблюдаемое состояние по SSE. Все адреса основного запуска привязаны к loopback.

## Запуск

Из корня проекта, Python 3.13. Для существующего окружения пропустите создание venv. Первый запуск устанавливает зависимости из PyPI. После установки режим demo работает локально.

**Windows, PowerShell**

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements/demo.txt
.\.venv\Scripts\python demo.py
```

**Linux и macOS**

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements/demo.txt
.venv/bin/python demo.py
```

Откройте [дом](http://127.0.0.1:8000), [OpenAPI решателя](http://127.0.0.1:8000/docs) или [диагностику шлюза](http://127.0.0.1:9000/ui). Начальная локальная учётная запись — `admin` / `admin`. При первом запуске пароль можно задать переменной среды `ADMIN_PASSWORD`. Войдите, откройте «Обзор → Профиль» и создайте приглашение для жильца. Для регистрации откройте форму «Есть приглашение» в другом окне. Пароль администратора при создании приглашения включает ограниченный по времени режим администратора.

По умолчанию `demo.py` собирает статический клиент, запускает два сервера и консольный эмулятор. В его терминале **e + Enter** вызывает E04, **l + Enter** — протечку. Ctrl+C завершает компоненты. Шлюз использует адаптер Godot, MQTT-брокер не нужен. При общем запуске панель шлюза показывает диагностику. Управление выполняется на основном сайте через правила и аудит FastAPI.

## Структура проекта

Код сгруппирован по подсистемам. Для решателя используется архитектура портов и адаптеров: доменные типы и правила живут в `backend/app/domain.py` и `backend/app/solver/`, контракты — в `backend/app/ports.py`, подключения — в `home/`, `storage/` и `rag/`. HTTP-маршруты связывают эти части в `api.py` и `integration.py`. Шлюз, веб-клиент и симуляция имеют собственные каталоги, поэтому участники могут работать в них независимо.

Тесты backend и шлюза находятся рядом со своими компонентами. Сквозные проверки вынесены в `tests/integration/`. Рабочие данные остаются в `runtime/`, исходные руководства — в `backend/data/manuals/`, а `myTestDir/` содержит личные материалы и эксперименты.

## Точки входа

| Каталог | Содержимое и запуск |
|---|---|
| `frontend/public/` | Русскоязычный клиент HTML/CSS/JS. `python demo.py --build-ui` копирует готовую статику в `runtime/frontend/`. Тот же шаг выполняет общий запуск. |
| `backend/` | Сервер `python -m uvicorn app.main:app` из каталога backend. В автономном режиме использует stub и память. Точка `python main.py` также запускает этот API. |
| `backend/app/rag/` | Индексация `python -m app.rag.indexer` из backend. Поиск и генерацию вызывает сервер. Исходные документы находятся в `backend/data/manuals/`. |
| `backend/app/storage/migrations/` | Версии схемы SQLite. Миграция 001 создаёт снимки, журнал и наблюдения при первом запуске. |
| `iot_gateway/` | `python -m uvicorn gateway.app:app --port 9000` из каталога шлюза. Реестр — `config/devices.json`, эмулятор — `tools/fake_godot.py`. |
| `godot_sim/` | Проект Godot 4, главная сцена `scenes/home.tscn`. Общий запуск с реальной сценой — `python demo.py --godot godot`. Можно указать полный путь к исполняемому файлу. |
| `tests/integration/` | Сквозные проверки HTTP, SQLite, симуляции и браузера с отдельными временными базами. |
| `requirements/` | Зависимости общей сборки: demo, check и rag. |
| `docs/` | Карта требований и результаты проверок. |
| `runtime/` | Генерируемая база, версии индекса, собранный клиент. Каталог исключён из публикации. |
| `myTestDir/` | Локальные черновики и эксперименты авторов. Не участвуют в запуске. |

Godot загружает `godot_sim/scripts/gateway_client.gd` как Autoload. Пример подключения котла находится в `godot_sim/examples/`. В `backend/data/manuals/` находятся руководства. Рабочая база и индекс Chroma создаются в `runtime/`. Общий запуск создаёт базу `runtime/home.sqlite3`, если она отсутствует. Повторный запуск читает ту же базу. Для отдельной демонстрации задайте новый путь `HOME_DB`. Переноса сторонних SQLite-схем в схему приложения нет.

## Chroma и локальная LLM

В режиме `demo` справку даёт детерминированный поиск по Markdown. В режиме `ollama` поиск использует Chroma и многоязычную MiniLM, ответ генерирует отдельный процесс Ollama. Выбор режима виден в заголовке чата. Шаблон `.env.example` описывает переменные среды. Launcher читает окружение процесса.

Установите Ollama, запустите её локальный сервис и один раз выполните `ollama pull qwen2.5:3b`. Веса Ollama и кеш Hugging Face находятся вне рабочей копии. В PowerShell из корня:

```powershell
.\.venv\Scripts\python -m pip install -r requirements/rag.txt
$env:RAG_DOWNLOAD = '1'
Push-Location backend
..\.venv\Scripts\python -m app.rag.indexer
Pop-Location
$env:ASSISTANT = 'ollama'
$env:OLLAMA_BASE_URL = 'http://127.0.0.1:11434'
$env:OLLAMA_MODEL = 'qwen2.5:3b'
$env:OLLAMA_NUM_GPU = '0'  # на проверенной машине GPU-запуск упирался в таймаут
.\.venv\Scripts\python demo.py --godot godot --video
```

По умолчанию запрос к Ollama ждёт до 90 секунд. Лимит меняется через `OLLAMA_TIMEOUT`. В Unix задайте те же переменные через `export`. Индексатор сначала строит новую версию, затем переключает файл CURRENT. В каждой записи хранятся имя документа, ID фрагмента, модель и код ошибки при наличии. Недоступность индекса или модели отображается ответом о деградации. Если установленный через WinGet Godot ещё не попал в PATH, передайте полный путь к `Godot_v*_win64.exe`.

## Контракты и ограничения

* `POST /api/auth/login` выдаёт короткий access и долгий refresh. Клиент передаёт access в заголовке Authorization: Bearer, включая GET /api/live. GET /api/home даёт снимок комнат, состояний, целей, расписаний и последних событий. После разрыва SSE клиент обновляет снимок и вновь открывает поток. Время расписаний и наблюдений — UTC.
* `POST /api/commands` принимает `device_id, operation, params`. Для кондиционера используйте `conditioner_living, turn_on, {}`. Сервер назначает impact_id для аудита, создаёт cmd_id и регистрирует ожидание до HTTP-вызова шлюза. `POST /commands` шлюза принимает объект с массивом commands и отвечает массивом results. Код HTTP 200 сам по себе не подтверждает действие. Требуются положительная квитанция и соответствующее ожидаемым параметрам состояние с тем же cmd_id. Повтор cmd_id в пределах жизни процесса шлюза получает прежний результат. После перезапуска решатель завершает прерванные ожидания со статусом «не подтверждено» без повторной отправки.
* `POST /api/gateway/events` требует X-Gateway-Token. Общий запуск создаёт случайный секрет процессов; тот же заголовок требуется для отправки команды на шлюз. Старый /api/events оставлен для stub. Событие содержит уникальный event_id, числовой device_id, kind (state, error, telemetry), UTC ts в секундах Unix, source=godot, payload и необязательный cmd_id. В SQLite сохраняются время возникновения и приёма. Отдельные события с устаревшей меткой сохраняются в истории без отката состояния. Критичные сообщения повторяются при отказе HTTP в пределах жизни шлюза. Очередь шлюза и кеш квитанций находятся в памяти.
* `POST /api/chat` принимает message. Ответ содержит kind, provider, reply, sources, иногда confirmation либо result. В демонстрационном словаре «включи кондиционер», «выключи кондиционер», «перекрой воду», «открой воду». Водяной клапан требует отдельного POST /api/chat/confirm/{confirmation_id} в течение 60 секунд. Разрешение связано с пользователем, ролью и исходной командой. Неоднозначное действие вызывает уточнение. Газовый котёл в состоянии ошибки блокируется решателем. Упомянутый в руководстве кран подпитки не является главным клапаном водоснабжения.
* Права и формы тел запросов для приглашений, отзыва сессий, смены пароля, целей, расписаний и блокировок перечислены в OpenAPI. SQLite рассчитана на один процесс решателя. Access-токены и подтверждения чата истекают при рестарте, пользователи, хеши кодов и долгих пропусков сохраняются.

| ID шлюза | Узел Godot → доменный ID | Смысл |
|---|---|---|
| 123 | Kitchen/Boiler → boiler | Демо-котёл на кухне. power on/off → bool; target_temp → уставка coolant_temperature °C. Измеренная temperature хранится отдельно. |
| 124 | Living/AC → conditioner_living | Кондиционер в гостиной. Передаёт собственное показание температуры воздуха, °C. |
| 125 | Bath/WaterValve → leak_protection | power on означает открытый главный клапан, off — закрытый. |
| 126 | Bath/LeakSensor → sensor_leak_bathroom | wet — булев признак протечки. WATER_LEAK также означает мокрый датчик. Влажность воздуха не эквивалентна протечке. |
| 127 | Spare/Lamp → light_spare | Запасная лампа. Питание on/off и яркость 1–100 %. |
| 128 | Living/Thermometer → sensor_temperature_living | Отдельное показание комнатного датчика, °C. |

Отображение, SQLite-снимки, локальная статика и узкий словарь ручных сценариев приняты при интеграции. Проверка реестра выполняется при построении модели. Симулятор отвечает за факты дома. При подключении он сообщает своё текущее состояние, которое может отличаться от сохранённого при предыдущем запуске.

## Сценарий видеозаписи

1. Запустите Ollama и демо с `--godot godot --video`. Разместите сайт слева, сцену справа. Дождитесь надписи «на связи» и времени обновления карточек.
2. На сайте нажмите «Включить» у кондиционера. В Godot значение power станет on, на сайте появится «Питание · да». Раскройте журнал, чтобы показать квитанцию и событие с идентификаторами.
3. Для отдельного прогона ошибки запустите консольный эмулятор и введите `e`. После появления E04 на карточке спросите в чате «Что означает E04?». Покажите объяснение и источник boiler_baxi.md. Проверьте надпись ollama в заголовке помощника.
4. Откройте плитку датчика в Godot, включите «Датчик мокрый» и сохраните. Сайт покажет мокрый датчик, решатель отправит закрытие клапана. Попытка открыть воду до осушения должна получить отказ. Для демонстрации цели задайте температуру гостиной, затем нажмите «Вернуть автоматику» на карточке кондиционера.

## Проверки

Установите `requirements/check.txt`. Из backend и iot_gateway запускайте отдельно `python -m pytest -o addopts='' -q`. Из корня — `python -m pytest -q tests/integration`. Браузерная проверка по умолчанию использует установленный Edge. На Unix установите браузер Playwright и выберите BROWSER_CHANNEL=chromium. Для видимого совместного запуска задайте SHOW_BROWSER=1 и SCENE_EXE (полный путь к Godot), затем выполните `python -m pytest -q tests/integration/test_browser.py`. Для проверки настоящего RAG и генерации добавьте CHECK_ASSISTANT=ollama после подготовки модели и индекса.

См. [карту требований и результаты](docs/acceptance.md).

### Исходники веб-интерфейса

Рабочая страница находится в `frontend/public/index.html`. В `home.js` этой папки находятся запросы к FastAPI, подписка на события и переключение разделов. Общие стили исходного макета находятся в `css/theme.css`, оформление рабочих форм и адаптивных карточек — в `style.css`, фон — в `img/bg.jpg`. Рабочий клиент загружает ресурсы локально.

Оригинал макета сохранён в `frontend/design-source/` вместе с HTML, CSS, JS и изображениями. Для изменений рабочего приложения используйте `frontend/public/`. Каталог `runtime/frontend/` заполняется при запуске.

После входа выберите комнату в «Обзоре» или откройте «Устройства» и выберите комнату на плане. Нажмите прибор для просмотра состояния и управления. Для сценария с E04 откройте «События», затем «Помощник». Цели и расписания находятся в «Обзор → Профиль → Автоматизация».


## Комнаты, подключение приборов и уставки

Под учётной записью администратора откройте «Устройства». Кнопка «Добавить комнату» создаёт помещение. Кнопка «Добавить устройство» показывает свободные приборы из каталога симулятора. Выберите прибор и комнату. Запасная лампа доступна для подключения при первом запуске, в том числе поверх существующей базы.

В карточке прибора можно изменить уставку воды котла (30–80 °C), уставку воздуха кондиционера (16–30 °C), его режим или яркость лампы (1–100 %). Текущая температура, давление и датчик протечки отображаются как показания. Настройка применяется по подтверждённой команде из симулятора.

«Отключить от дома» убирает прибор из комнаты и возвращает его в список подключения. Физическое состояние модели при этом сохраняется. Связанные правила автоматизации снимаются. Пустую комнату можно удалить из её экрана. При отключённом датчике протечки ручное открытие клапана блокируется. Комнаты, подключения и привязка к помещениям сохраняются в SQLite. Датчик температуры можно подключать, переносить и отключать отдельно от кондиционера.

API каталога: `GET /api/catalog/available`, `POST /api/rooms`, `DELETE /api/rooms/{room_id}`, `PUT /api/devices/{device_id}/connection`. В запросе подключения передаётся `room_id`, при отключении — `null`.

## Сценарии в симуляторе

В Godot состояние прибора меняется через форму на его плитке. Для проверки защиты откройте датчик протечки и переключите поле «Датчик мокрый».

В консольном эмуляторе введите `e` для ошибки E04, `r` для восстановления давления, `l` для протечки или `d` для сухого датчика. Нажмите Enter. После восстановления давления используйте «Сбросить ошибку» на сайте.

### Плитки устройств в Godot

Запустите `python demo.py --godot godot --video`. Устройства отображаются одинаковыми плитками. Нажмите плитку, чтобы изменить настройки или состояние прибора. Плитка «+ Добавить устройство» открывает выбор типа и форму с параметрами. Типы включают котёл, кондиционер, клапан, датчик протечки, датчик температуры и лампу. Новые приборы сохраняются в каталоге Godot `user://virtual_devices.cfg` и повторно объявляются при переподключении шлюза.

После добавления прибора откройте на сайте под администратором «Устройства → Добавить устройство». Выберите созданный прибор и комнату. До подключения он отображается в списке доступных. Комната и подключение хранятся в SQLite. Редактирование из окна Godot моделирует изменение на стороне прибора, а сайт получает наблюдаемое состояние через шлюз и SSE.

Чтобы проверить создание и подключение нового прибора в браузерном тесте с Godot, задайте `SCENE_EXE` и `CHECK_GODOT_CATALOG=1`. Для теста используется временный каталог приборов. Для другого запуска можно задать отдельный путь `SIM_INVENTORY_PATH`.


Чтобы удалить прибор из симулятора, откройте его плитку и нажмите «Удалить устройство». После подтверждения прибор пропадает из комнаты и списка подключения на сайте. Связанная автоматизация снимается, история событий сохраняется. Удаление сохраняется при перезапуске Godot. Если шлюз недоступен, Godot отправит его при восстановлении соединения.

#### Физические параметры в Godot

- Котёл: задайте текущую температуру воды и давление. При давлении ниже 1 бар симулятор отключает котёл и отправляет E04. После восстановления давления сбросьте ошибку на сайте.
- Кондиционер: задайте текущую температуру воздуха отдельно от уставки. Для котла и кондиционера можно включить удержание температуры. При выключенном удержании значение снова меняется по модели.
- Датчик температуры: снимите «Следовать за температурой воздуха в гостиной», чтобы выдавать заданное вручную показание. Это показание может использовать автоматика комнаты, в которой подключён датчик.
- Датчик протечки: измените признак протечки и заряд батареи. Заряд отображается как диагностическое показание.
- Лампа и клапан: отключение питания от сети гасит лампу с сохранением яркости. Заклинивший клапан удерживает текущее положение и отклоняет команды.

На сайте физические параметры доступны для просмотра. Уставки и режимы по-прежнему задаются командами.

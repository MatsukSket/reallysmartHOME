# Решатель задач интеллектуальной системы «Умный дом»

Серверная часть курсового проекта. Основная работа --- единый путь
выполнения команд и автоматизация: расписания и целевые значения.

## Запуск

Решатель находится в папке `backend` и запускается оттуда.

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements-solver.txt
.venv/bin/python -m pytest -q
.venv/bin/uvicorn app.main:app --reload
```

Документация API открывается по адресу `http://127.0.0.1:8000/docs`.

## Что уже работает

**Единый путь команды.** Проверка устройства, операции, диапазона
параметров, состояния ошибки, проверок безопасности и конфликта с
блокировкой. Статусы: «выполнено», «не требуется», «отклонено»,
«не подтверждено». Ожидание подтверждения не дольше Tк, без повторов.

**Ожидание не блокирует дом.** Общая блокировка берётся только на время
проверки и записи. Само ожидание ответа модели, отправка команды и
публикация событий идут без неё, поэтому один молчащий прибор не
останавливает приём событий, выполнение расписаний и ответы остальным
пользователям. Если подтверждение приходит отдельным запросом модели,
ожидающий просыпается сразу, не досиживая до конца отведённого времени.
Команды автоматики не ждут вовсе: их подтверждение приходит событием.
Просроченные команды помечаются неподтверждёнными фоновой проверкой и не
висят в памяти вечно.

**Очередь к одному устройству.** У каждого устройства своя блокировка.
Благодаря ей проверка и отправка команды одному устройству выполняются
строго по очереди: ручная команда и расписание не могут проскочить
одновременно. При проверке учитывается не только сохранённое состояние,
но и ожидаемое, поэтому две одинаковые одновременные команды уходят
модели один раз. Команды разным устройствам друг друга не ждут.

**Проверка устаревания.** Команда не выполняется, если сведения, от
которых зависит безопасность, устарели. Например, открыть воду нельзя,
когда датчик протечки молчит дольше допустимого: неизвестно, сухо ли
сейчас.

**Внутренняя шина событий.** Модули не вызывают друг друга напрямую:
они публикуют события, а заинтересованные подписчики на них реагируют.
Виды событий: получено показание, изменилось состояние, появилась
ошибка, команда завершена, сработало расписание, изменилось целевое
значение, сообщение отброшено, прошла минута. Новый подписчик, например
правило безопасности, добавляется без правки ядра. Ошибка одного
подписчика не мешает остальным, вложенная публикация ограничена по
глубине.

**Журнал.** Каждый запрос получает идентификатор воздействия, по
которому видна вся цепочка: что пришло, что проверялось, чем
закончилось. В журнал пишутся команда и её итог, постановка и снятие
блокировки, изменение целевого значения, отброшенные сообщения и отказы
компонентов.

**Живые обновления.** Клиент получает изменения сразу потоком, без
обновления страницы. Последние события можно догнать отдельным
запросом, если соединение прерывалось.

**Вход и роли.** Жилец попадает в систему по приглашению от
администратора: администратор создаёт приглашение и передаёт одноразовую
ссылку, жилец по ней задаёт пароль.

Дальше вход устроен как в домашних системах управления: при входе
выдаются два пропуска. Короткий прикладывается к каждому запросу и живёт
полчаса. Долгий хранится на устройстве и служит для получения нового
короткого; он продлевается при каждом использовании. Поэтому пароль
вводится один раз на устройстве, а не каждый день. Срок долгого пропуска
нужен не для того, чтобы выкидывать человека, а чтобы потерянное
устройство можно было отключить: в профиле виден список устройств, любое
можно отозвать, а смена пароля отключает все остальные.

Пароли и коды приглашений хранятся только в виде хэшей. Действия,
меняющие состав дома и список пользователей, требуют режима
администратора — повторного ввода пароля, действующего ограниченное
время. Журнал показывает, кто выполнил действие.

**Фоновая работа.** Решатель действует сам, без внешних запросов: раз в
секунду он продвигает симуляцию модели, принимает накопившиеся события и
проверяет наступившие расписания. Цикл запускается вместе с сервером и
останавливается при его завершении. Служебный запрос прокрутки остался
для тестов и демонстрации.

**Блокировка.** Ставится ручной командой и подтверждённым предложением
помощника. Снимается тремя способами: таймер (20 минут для света, 2 часа
для остальных), срабатывание расписания этого устройства, кнопка «вернуть
автоматику». Противоречие --- изменение того же свойства на другое
значение.

**Целевые значения.** Зона нечувствительности 0,5 °C для температуры и
5 % для влажности. Регулирующее устройство указывается при создании цели.
Направление регулирования учитывается: обогреватель включается при
холоде, кондиционер --- при жаре.

**Расписание целевой температуры.** Пользователь указывает, к какому
времени нужна заданная температура и до какого времени её держать. Оба
времени обязательны. Решатель вычитает упреждение 20 минут и создаёт два
момента: привести температуру заранее и вернуть обычное значение.
Для устройства, управляемого целевым значением, расписание команды не
создаётся.

**События и ошибки.** Проверка значения, отбрасывание повторов по тройке
«устройство, вид, время» и запоздавших событий. Ошибка снимается
следующим нормальным событием; ошибка котла требует явного сброса.
Неактуальность считается по времени получения события решателем.

**Безопасность.** Открыть воду нельзя, пока датчик протечки показывает
воду. Пылесос не запускается при заряде ниже 20 % и в помещении с
протечкой. Уборка подтверждается сменой режима, окончание приходит
отдельным событием.

## Заглушки

Выбор компонента выполняется настройками окружения, порт у заглушки и
настоящего компонента общий:

```
HOME_MODEL=stub     # stub | egor
STORAGE=memory      # memory | maxim
```

Режимы заглушки модели: `normal`, `silence`, `error`, `garbage`,
`duplicate`, `unavailable`. Заглушки после замены не выбрасываются: на них
идут тесты и аварийная демонстрация.

## Тесты

191 проверка, время выполнения около тринадцати секунд: часть времени
уходит на хэширование паролей. Расписания и ожидание команды проверяются
на управляемых часах, поэтому реального ожидания нет. Отдельные наборы
проверяют работу под нагрузкой, шину событий, журнал, вход и фоновую
работу.

```
backend/tests/
  test_commands.py      единый путь команды и режимы модели
  test_locks.py         блокировки и определение противоречия
  test_events.py        приём событий, ошибки, неактуальность
  test_maintenance.py   поддержание целевого значения
  test_schedules.py     расписания, упреждение, возврат цели
  test_safety.py        протечка, пылесос, розетка
  test_api.py           запросы API, вход и права
  test_auth.py          пароли, приглашения, пропуска, роли
  test_background.py    фоновая работа
  test_scenarios.py     сквозные сценарии
  test_concurrency.py   ожидание команды не блокирует решатель
  test_queue.py         очередь команд к одному устройству
  test_bus.py           шина событий
  test_journal.py       журнал и живые обновления
```


## Как решатель сосуществует с остальными частями

В папке `backend/app` уже находятся чужие модули, и решатель ничего в них
не меняет:

```
app/rag/         хранилище контекста и знаний (Захар)
app/schemas/     схемы ответа интеллектуального модуля (Захар)
app/api.py       решатель
app/solver/      ядро решателя
app/domain.py    типы устройств и команд решателя
```

Пересечений нет: `app/rag` и `app/schemas` оставлены как есть, файлы
решателя лежат рядом. Импорты внутри решателя относительные, поэтому он
работает из этой папки без изменений.

**Что ещё не соединено.** Хранилище знаний и интеллектуальный модуль в
решателе объявлены портами (`app/ports.py`), но пока не подключены к
`app/rag` и `app/schemas`. Это следующий шаг: нужен адаптер, который
передаёт вопрос в `get_context` Захара и получает ответ в формате
`SolverResponse`.

**Что нужно согласовать с Захаром.** Сейчас `get_context` возвращает
готовую строку с фрагментами. Решателю удобнее получить список
фрагментов с источниками отдельно. Кроме того, в `SolverResponse` нет
варианта «уточняющий вопрос», а он нужен, когда устройство не удалось
определить однозначно.

**Что нужно согласовать с Максимом.** Файл `data/home.db` в репозитории
пустой: таблицы ещё не созданы. Решатель пока держит данные в памяти
(`app/storage/memory.py`). Требования к таблицам описаны отдельно, схема
согласуется.

**Приём событий от модели.** Запрос `POST /api/events` сейчас открыт:
события присылает не человек, а внешний компонент. При подключении модели
Егора этот канал нужно защитить общим секретом.

## Первый администратор

Создаётся при запуске из настроек:

```
ADMIN_NAME=admin
ADMIN_PASSWORD=admin
```

Без первого администратора приглашать новых пользователей было бы
некому. Пароль по умолчанию нужно сменить перед показом системы
посторонним.
